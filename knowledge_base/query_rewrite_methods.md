# KNOWLEDGE_BASE: DATABASE_APPLICATION_QUERY_REWRITE_AND_OPTIMIZATION

## 1. COMBINING_QUERIES

* **Definition**: Combining multiple database operations into fewer SQL statements or a single set-oriented operation.
* **Objective**: Reduce database round-trips, query execution overhead, and repeated scans.
* **Mechanisms**:

  * Combining multiple related `SELECT` operations into a single `JOIN`.
  * Replacing multiple point lookups with a single `IN (...)` or set-based query.
  * Merging compatible queries that access the same tables and predicates.
  * Replacing sequential dependent queries with a single SQL statement when the dependency can be expressed relationally.
  * Combining repeated queries generated by application loops into batch operations.
* **Risks**:

  * Larger intermediate result sets.
  * Changed duplicate-row semantics.
  * Increased query complexity.
  * Changed transaction or locking behavior.

## 2. N_PLUS_ONE_QUERY_ELIMINATION

* **Definition**: Eliminating repeated database queries issued once per application object, typically from loops.
* **Objective**: Reduce database round-trips and repeated query execution overhead.
* **Mechanisms**:

  * Replacing per-record queries with `JOIN` operations.
  * Replacing repeated point lookups with `IN (...)` batch queries.
  * Fetching related records using a single set-oriented query.
  * Replacing ORM lazy-loading loops with eager loading or explicit batch fetching.
  * Grouping requested identifiers and issuing one database operation per batch.
* **Risks**:

  * Excessively large result sets.
  * Duplicate rows introduced by joins.
  * Increased application memory usage.
  * Different ORM object-loading behavior.

## 3. QUERY_BATCHING

* **Definition**: Replacing many individual database operations with a smaller number of set-oriented or bulk operations.
* **Objective**: Reduce network round-trips and per-query execution overhead.
* **Mechanisms**:

  * Replace repeated `SELECT ... WHERE id = ?` operations with `WHERE id IN (...)`.
  * Replace repeated inserts with multi-row `INSERT`.
  * Replace repeated updates with batch or set-based `UPDATE`.
  * Use database-driver batch APIs such as `executemany` where appropriate.
  * Push reduction into SQL: reduce in the database with `MIN`/`MAX`/`SUM`/`COUNT` ... `GROUP BY` rather than fetching the full batch and reducing in Python.
  * Prefer a single batch statement. Never place a database call inside a loop (including a chunking loop) — the strict-zero rewrite contract forbids it.
  * When combining queries, keep the plan simple: prefer a plain `JOIN` or scalar subqueries in `WHERE`; avoid cross-joining a derived table in `FROM`, which can make per-execution planning time dominate and slow the "optimized" code down.
* **Risks**:

  * Parameter-count limits.
  * Excessive query size.
  * Larger transaction scope.
  * Increased lock duration.
  * Increased memory consumption.

## 4. REDUNDANT_QUERY_ELIMINATION

* **Definition**: Removing database operations whose results are duplicated, unused, or already available to the application.
* **Objective**: Eliminate unnecessary database work and network traffic.
* **Mechanisms**:

  * Detecting repeated identical queries within the same execution path.
  * Reusing previously fetched results when transaction and consistency semantics permit.
  * Removing queries whose returned values are never consumed.
  * Combining queries that repeatedly retrieve overlapping data.
  * Avoiding duplicate existence or lookup checks.
* **Risks**:

  * Reusing stale data.
  * Changed transaction visibility.
  * Changed behavior when database state can change between queries.

## 5. PREDICATE_PUSHDOWN

* **Definition**: Moving filtering operations as close as possible to the database access operation or underlying data source.
* **Objective**: Reduce rows transferred, processed, joined, and materialized.
* **Mechanisms**:

  * Move application-side filtering into SQL `WHERE` predicates.
  * Apply predicates before expensive joins or aggregations.
  * Push predicates through derived tables or compatible subqueries.
  * Apply selective filters before transferring data to the application.
  * Combine compatible predicates to reduce intermediate cardinality.
* **Risks**:

  * Changed `NULL` semantics.
  * Changed outer-join behavior.
  * Side effects or non-deterministic expressions.
  * Predicates that cannot be safely evaluated earlier.

## 6. PROJECTION_PUSHDOWN

* **Definition**: Selecting only the columns required by downstream SQL operations or application logic.
* **Objective**: Reduce I/O, network transfer, serialization, and application memory consumption.
* **Mechanisms**:

  * Replace `SELECT *` with explicitly required columns.
  * Remove unused columns from subqueries and intermediate results.
  * Propagate required-column information through query operators.
  * Fetch only fields consumed by the application.
* **Risks**:

  * Removing columns that are implicitly required by application logic.
  * Breaking ORM hydration or serialization behavior.
  * Removing columns needed by downstream expressions.

## 7. APPLICATION_LOGIC_PUSHDOWN

* **Definition**: Moving database-compatible application processing into SQL so that computation occurs closer to the stored data.
* **Objective**: Reduce data transfer and application-side processing.
* **Mechanisms**:

  * Python/application filtering → SQL `WHERE`.
  * Application counting → SQL `COUNT`.
  * Application aggregation → SQL `GROUP BY`.
  * Application sorting → SQL `ORDER BY`.
  * Application existence checks → SQL `EXISTS`.
  * Application deduplication → SQL `DISTINCT`.
* **Risks**:

  * Semantic differences between application and SQL operations.
  * Database CPU becoming the bottleneck.
  * Differences in floating-point, `NULL`, collation, or type semantics.

## 8. SUBQUERY_REWRITE

* **Definition**: Transforming subqueries into equivalent relational expressions that provide the database optimizer with a more favorable query structure.
* **Objective**: Improve join optimization opportunities and reduce repeated or correlated execution.
* **Mechanisms**:

  * Rewrite correlated subqueries as joins where semantic equivalence is guaranteed.
  * Rewrite scalar subqueries into joins or pre-aggregated relations.
  * Rewrite compatible nested subqueries into derived tables.
  * Eliminate unnecessary levels of query nesting.
* **Risks**:

  * Duplicate rows introduced by joins.
  * Changed scalar-subquery cardinality semantics.
  * `NULL` behavior changes.
  * Correlation dependencies being incorrectly removed.

## 9. EXISTS_AND_IN_REWRITE

* **Definition**: Rewriting membership and existence predicates into equivalent semi-join or anti-join forms.
* **Objective**: Expose set-based execution opportunities and avoid unnecessary result materialization.
* **Mechanisms**:

  * `IN` → `EXISTS` where equivalence is established.
  * `EXISTS` → semi-join representation.
  * `NOT EXISTS` → anti-join representation.
  * Rewrite membership tests into joins when duplicate and `NULL` semantics permit.
* **Risks**:

  * `NULL` semantics.
  * Duplicate-row semantics.
  * Differences between `IN`, `EXISTS`, and join behavior.

## 10. NOT_IN_TO_ANTI_JOIN

* **Definition**: Rewriting `NOT IN` predicates into `NOT EXISTS` or anti-join forms when SQL three-valued logic is preserved.
* **Objective**: Enable efficient anti-join execution while preserving exact SQL semantics.
* **Mechanisms**:

  * Rewrite `NOT IN` to `NOT EXISTS` when the inner expression is guaranteed non-null.
  * Add explicit `IS NOT NULL` guards when required.
  * Represent the operation as an anti-join when supported by the target database.
* **Risks**:

  * Incorrect results when the inner relation can contain `NULL`.
  * Duplicate and three-valued-logic differences.
* **Safety Requirement**: Never apply this transformation without checking `NULL` semantics.

## 11. OR_TO_UNION

* **Definition**: Rewriting disjunctive predicates into multiple relational branches using `UNION` or `UNION ALL`.
* **Objective**: Enable independent predicate evaluation and potentially improve access-path selection.
* **Mechanisms**:

  * Rewrite `P OR Q` as separate queries when the branches are semantically compatible.
  * Use `UNION ALL` when branches are mutually exclusive or duplicate preservation is explicitly safe.
  * Use `UNION` when duplicate elimination is required.
  * Add guard predicates when necessary to make branches mutually exclusive.
* **Risks**:

  * Duplicate rows.
  * Increased scans.
  * Changed `NULL` behavior.
  * Increased query complexity.

## 12. UNION_OPTIMIZATION

* **Definition**: Optimizing set operations by preserving duplicate semantics while avoiding unnecessary duplicate elimination.
* **Objective**: Reduce sorting, hashing, and duplicate-removal overhead.
* **Mechanisms**:

  * Replace `UNION` with `UNION ALL` when duplicate elimination is provably unnecessary.
  * Remove redundant branches.
  * Simplify compatible predicates across union branches.
* **Risks**:

  * Incorrect duplicate semantics.
  * Different result cardinality.

## 13. CTE_OPTIMIZATION

* **Definition**: Optimizing Common Table Expressions by determining whether they should be inlined, simplified, or materialized.
* **Objective**: Expose optimization opportunities or avoid repeated computation.
* **Mechanisms**:

  * Inline CTEs when additional predicate or join optimization can be exposed.
  * Remove unused CTEs.
  * Simplify CTE expressions.
  * Materialize CTE results when repeated computation makes materialization beneficial and semantics permit it.
* **Risks**:

  * Repeated computation after inlining.
  * Unnecessary materialization.
  * Changed optimization boundaries.

## 14. JOIN_ORDER_OPTIMIZATION

* **Definition**: Restructuring joins to reduce intermediate result cardinality and execution cost.
* **Objective**: Reduce expensive intermediate relations and improve overall query execution.
* **Mechanisms**:

  * Apply highly selective predicates before joining large relations.
  * Join smaller or more selective relations earlier when the database optimizer can benefit from the exposed structure.
  * Rewrite nested queries to expose join relationships.
  * Pre-aggregate large relations before joining when semantics permit.
* **Risks**:

  * The database optimizer may already determine a better join order.
  * Query restructuring may have no effect on the final execution plan.
  * Incorrect assumptions about cardinality can make the transformation harmful.

## 15. JOIN_TYPE_OPTIMIZATION

* **Definition**: Replacing a join with a semantically equivalent join type or relational operation.
* **Objective**: Reduce unnecessary row production and expose more efficient execution strategies.
* **Mechanisms**:

  * `JOIN` → `EXISTS` / semi-join when only existence is required.
  * `JOIN` → anti-join when only non-existence is required.
  * Remove joins whose columns and predicates do not affect the result.
  * Replace unnecessary outer joins with inner joins when null-preserving behavior is provably irrelevant.
* **Risks**:

  * Duplicate rows.
  * Outer-join semantics.
  * `NULL` behavior.
  * Referential-integrity assumptions.

## 16. JOIN_ELIMINATION

* **Definition**: Removing joins that do not contribute observable data or filtering to the final result.
* **Objective**: Reduce scans, joins, and intermediate result generation.
* **Mechanisms**:

  * Remove tables whose columns are not consumed.
  * Remove existence-only joins when equivalent constraints guarantee the relationship.
  * Remove redundant joins introduced by ORM-generated SQL.
* **Risks**:

  * The join may implicitly filter rows.
  * Referential-integrity assumptions may not hold.
  * Join predicates may affect duplicate cardinality.

## 17. PRE_AGGREGATION_BEFORE_JOIN

* **Definition**: Aggregating a relation before joining it with another relation when the aggregation can be safely pushed below the join.
* **Objective**: Reduce the number of rows participating in expensive joins.
* **Mechanisms**:

  * Apply `GROUP BY` before joining large relations.
  * Aggregate fact/detail rows before joining dimension or lookup tables.
  * Move compatible aggregation below joins when grouping keys preserve semantics.
* **Risks**:

  * Incorrect grouping keys.
  * Changed duplicate semantics.
  * Aggregates that depend on rows from both sides of a join.

## 18. SARGABILITY_OPTIMIZATION

* **Definition**: Rewriting predicates so that database access methods can efficiently evaluate them using available indexes or other access paths.
* **Objective**: Avoid unnecessary full scans and make predicates more directly searchable.
* **Mechanisms**:

  * Remove functions from indexed columns where an equivalent range predicate exists.
  * Rewrite arithmetic expressions on indexed columns.
  * Avoid unnecessary casts on indexed columns.
  * Rewrite date extraction into range predicates where semantics permit.
  * Avoid leading-wildcard patterns when an equivalent searchable predicate exists.
* **Risks**:

  * Time-zone differences.
  * Type-conversion semantics.
  * Collation differences.
  * Incorrect range boundaries.

## 19. SELECT_STAR_ELIMINATION

* **Definition**: Replacing `SELECT *` with the explicit set of columns required by the application or downstream query.
* **Objective**: Reduce data transfer, serialization, memory consumption, and unnecessary database work.
* **Mechanisms**:

  * Analyze application field access.
  * Remove unused columns.
  * Propagate required-column information through nested queries.
* **Risks**:

  * Dynamic consumers may depend on additional columns.
  * ORM or serialization behavior may rely on complete result sets.

## 20. LIMIT_AND_TOP_N_PUSHDOWN

* **Definition**: Moving row-count restrictions closer to the database operation that produces the required result.
* **Objective**: Reduce rows processed, transferred, and materialized.
* **Mechanisms**:

  * Application-side slicing → SQL `LIMIT`.
  * Push compatible limits through subqueries.
  * Combine `ORDER BY` and `LIMIT` into Top-N execution opportunities.
* **Risks**:

  * Incorrect ordering.
  * Limit pushed across joins or aggregations without semantic equivalence.
  * Different tie-breaking behavior.

## 21. REDUNDANT_OPERATION_ELIMINATION

* **Definition**: Removing SQL or application operations that do not affect the observable result.
* **Objective**: Reduce unnecessary computation.
* **Mechanisms**:

  * Remove redundant predicates.
  * Remove duplicate projections.
  * Remove unnecessary `DISTINCT`.
  * Remove redundant sorting when ordering is not observable.
  * Remove unused subqueries or CTEs.
  * Remove unnecessary existence checks.
* **Risks**:

  * Hidden dependencies.
  * Ordering requirements.
  * Duplicate semantics.
  * Application behavior depending on intermediate results.

## 22. APPLICATION_SIDE_AGGREGATION_TO_SQL

* **Definition**: Replacing application-side aggregation over database results with equivalent SQL aggregation.
* **Objective**: Reduce result-set size and application CPU/memory usage.
* **Mechanisms**:

  * Python `sum()` → SQL `SUM()`.
  * Python `count()` → SQL `COUNT()`.
  * Application grouping → SQL `GROUP BY`.
  * Application minimum/maximum → SQL `MIN()` / `MAX()`.
  * Application deduplication → SQL `DISTINCT`.
* **Risks**:

  * Numeric precision differences.
  * `NULL` behavior.
  * Empty-set behavior.
  * Ordering assumptions.

## 23. APPLICATION_SIDE_SORTING_TO_SQL

* **Definition**: Moving sorting of database-derived data from application code into SQL.
* **Objective**: Reduce data transfer and application memory/CPU usage.
* **Mechanisms**:

  * Python `sorted()` → SQL `ORDER BY`.
  * Push compatible sort keys into the SQL query.
  * Combine sorting with `LIMIT` for Top-N retrieval.
* **Risks**:

  * Different collation.
  * Different `NULL` ordering.
  * Different type-comparison semantics.
  * Application-specific comparator logic.

## 24. ROUND_TRIP_REDUCTION

* **Definition**: Reducing the number of network interactions between application code and the database.
* **Objective**: Reduce network latency and per-query protocol overhead.
* **Mechanisms**:

  * Combine queries.
  * Batch database operations.
  * Eliminate N+1 queries.
  * Reuse previously retrieved results.
  * Replace sequential dependent queries with set-based SQL where possible.
* **Risks**:

  * Larger queries.
  * Larger result sets.
  * Changed transaction boundaries.

## 25. INDEPENDENT_QUERY_PARALLELISM

* **Definition**: Executing independent database operations concurrently when they have no data or ordering dependencies.
* **Objective**: Reduce wall-clock latency for application operations containing independent database calls.
* **Mechanisms**:

  * Identify independent queries in application control flow.
  * Execute independent operations concurrently using appropriate asynchronous database APIs or connection mechanisms.
  * Preserve dependency ordering for queries that require previous results.
* **Risks**:

  * Connection exhaustion.
  * Transaction semantics.
  * Lock contention.
  * Increased database concurrency.
  * Queries that appear independent but share transactional state.

## 26. LOOP_TO_SET_OPERATION

* **Definition**: Replacing application loops that perform repeated database operations with set-oriented SQL operations.
* **Objective**: Eliminate per-item database execution overhead.
* **Mechanisms**:

  * Loop of `SELECT` → `IN`, `JOIN`, or `EXISTS`.
  * Loop of `INSERT` → bulk insert.
  * Loop of `UPDATE` → set-based `UPDATE`.
  * Loop of existence checks → `EXISTS` or semi-join.
* **Risks**:

  * Different per-item error handling.
  * Different transaction behavior.
  * Large intermediate result sets.
  * Different ordering of side effects.

## 27. RESULT_SET_REDUCTION

* **Definition**: Reducing the amount of data returned from the database to the application.
* **Objective**: Reduce network transfer, deserialization, memory consumption, and application processing.
* **Mechanisms**:

  * Select only required columns.
  * Push filtering into SQL.
  * Push aggregation into SQL.
  * Apply `LIMIT` when only a bounded number of results is required.
  * Replace full-row retrieval with existence checks where row contents are not required.
* **Risks**:

  * Missing data required by downstream application logic.
  * Incorrect assumptions about future result consumption.

## 28. SQL_SEMANTIC_SAFETY

* **Definition**: Constraints that must be checked before applying an automated SQL or application transformation.
* **Objective**: Ensure optimization preserves observable application and database behavior.
* **Mechanisms**:

  * Preserve `NULL` semantics.
  * Preserve duplicate/bag semantics.
  * Preserve outer-join semantics.
  * Preserve aggregation semantics.
  * Preserve ordering when ordering is observable.
  * Preserve transaction behavior.
  * Preserve error behavior where application logic depends on it.
  * Preserve side-effect behavior and evaluation constraints.
* **Safety Rule**: An optimization must not be applied solely because two queries appear logically similar. Required semantic preconditions must be established first.

## 29. OPTIMIZATION_SELECTION

* **Definition**: Selecting candidate transformations based on the observed application and SQL execution pattern rather than applying rewrites indiscriminately.
* **Objective**: Apply only transformations with a plausible performance benefit and satisfied semantic preconditions.
* **Mechanisms**:

  * Detect optimization opportunities from application source code.
  * Detect repeated or N+1 query patterns.
  * Analyze SQL structure and execution plans when available.
  * Generate candidate rewrites from applicable KB rules.
  * Check transformation preconditions.
  * Prefer transformations that reduce database round-trips, intermediate cardinality, or unnecessary application processing.
  * Reject transformations whose semantic requirements cannot be established.
* **Decision Factors**:

  * Query frequency.
  * Number of database round-trips.
  * Estimated intermediate cardinality.
  * Result-set size.
  * Query complexity.
  * Transformation safety.
  * Expected reduction in database or application work.

## 30. VERIFICATION

* **Definition**: Validating that an optimization preserves application behavior and produces an acceptable execution strategy.
* **Objective**: Prevent incorrect rewrites and performance regressions.
* **Mechanisms**:

  * Compare original and optimized SQL results.
  * Check row counts and returned values.
  * Check `NULL` and duplicate behavior.
  * Compare `EXPLAIN` plans when available.
  * Compare estimated cardinalities.
  * Validate application tests after source-code transformations.
  * Reject transformations that cannot be shown to preserve required semantics.
* **Verification Principle**: Semantic correctness must be established before treating a transformation as a valid optimization.

## 31. COMPOSITE_KEY_BATCH_LOOKUP

* **Definition**: Replace per-row SELECT queries inside a loop (where rows are identified by 2+ columns) with a single batch query using a multi-column tuple IN clause, then re-index results into a composite-key lookup dictionary.
* **Objective**: Reduce N per-row DB round-trips to exactly one batch query (never a loop of chunked queries).
* **Conditions**: Loop fetches rows by (col_a, col_b) per iteration; all pairs are known before loop entry; database supports tuple IN syntax (PostgreSQL, MySQL 5.7+, SQLite 3.15+).
* **Mechanisms**:
  * Collect `(a_val, b_val)` pairs before the loop
  * Build `pair_ph = "(%s,%s)"` or `"(?,?)"` per detected dialect
  * `placeholders = ", ".join([pair_ph] * len(pairs))`
  * `flat_params = [v for pair in pairs for v in pair]`
  * If SELECT list includes a dynamic column name (e.g. `"col_%02d" % idx`): format it into a variable FIRST, then concatenate into SQL with `+` — never apply `%` to a template containing `%s`/`?` placeholders
  * Index results: `{(row[0], row[1]): row[2:] for row in cursor.fetchall()}`
  * In loop: `lookup.get((a_val, b_val))` — zero `cursor.execute` calls
  * When the batched write is a read-modify-write, preserve sequential accumulation: if duplicate keys are possible, aggregate deltas per key in memory before the batch write (do not assume keys are unique).
  * Preserve failure semantics: keep every `assert` and its condition; the rewrite must be behavior-preserving (do not fix unrelated pre-existing bugs).
* **Risks**:
  * Parameter-count limits — a single batch query must stay within the driver limit; never wrap batch execution in a loop to chunk it (strict-zero forbids DB calls inside loops)
  * Tuple-IN not supported by all driver versions — verify before applying
  * Result rows may differ in order — always look up by composite key, not by index
  * Large batches increase transaction scope and lock duration
* **Safety**: Include both key columns as first two SELECT columns. Use `.get()` not `[]` to preserve None-handling. Never mix `%s` and `?` placeholders in the same query. The SELECT list MUST contain every column used as a lookup key, and every `row[i]` index read must be within the SELECT column list — indexing a column the query does not select raises `IndexError: tuple index out of range` at runtime. For read-modify-write batches, aggregate duplicate-key deltas before writing, and preserve all `assert`/failure semantics.
